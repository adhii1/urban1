# Client Portal Identity and OTP Bugfix Design

## Overview

Three defect families are in scope, and they share one shape: the server is mostly right and the
client either never asks or throws the answer away.

**Rider identity** is a capture-and-correction failure, not a caching one. `utils/userCache.js` keys
strictly by `String(userId)` and `config/socket.js:313` resolves per connection, so no customer's
name can reach another customer. What is broken is that a name is never reliably *captured*
(`client/app/customer/(marketing)/page.tsx:72` has no `required`), a blank one is *replaced by a
generated placeholder* (`services/authService.js:145-147`), a supplied one is *discarded for an
existing user* (`services/authService.js:148-153`), and it can *never be corrected* because
`PUT /customer/profile` destructures only the three location fields
(`controllers/customerController.js:227`). Eight downstream placeholder literals then collapse the
whole population into what looks like one repeated rider. The fix closes the capture gap, opens a
correction path, centralises one placeholder predicate and one identity resolver, and removes every
fabricated label so an unresolved rider renders as a visibly distinct "details unavailable" state.

**Boarding OTP** is purely a client gap. `controllers/rideController.js` `getMyRides`,
`getRideById` and `getActiveRide` all return `otp.code` and all filter on `customerId: req.user.id`,
so disclosure is already correctly scoped — it is simply never read. There is no hook for
`/rides/my` or `/rides/active` in `client/lib/hooks/useCustomerQueries.ts`;
`client/lib/hooks/useRideBooking.ts` holds the code in `activeRide` but discloses it only through a
dismissible toast. The fix adds a typed ride data layer, a single reusable `BoardingCode` component
shared by all three customer surfaces, and socket-driven refetch so the code survives a reload.
Those same endpoints currently also hand the customer driver-internal `matchedDrivers`; this design
narrows that, because nothing under `client/` or either static frontend reads it.

**Unfinished integration** is server capability with no caller: `PUT /api/v1/driver/trips/status`
(mounted `routes/v1/driverRoutes.js:17`, handler `controllers/driverController.js:449`, transition
table `:438-446`) has zero callers under `client/`, boarding-code entry runs through
`window.prompt`, `DriverProfile` omits six fields the endpoint returns, the wallet is hardcoded to
`₹ 0.00`, the dashboard swallows errors with `.catch(() => {})`, and document upload cannot work
because `config/config.js:132` points at a relative `'src/uploads'` that does not exist, the
controller advertises `/uploads/documents/<file>` while its own `UPLOAD_DIR` sits one level above
the project root, and `app.js` never mounts `/uploads`.

The approach throughout is: one shared predicate or component per concern rather than a fix per
call site, and a contract assertion in `scripts/contractCheck.js` for each invariant that would
otherwise decay silently.

## Glossary

- **Bug_Condition (C)** — an interaction where a rider's identity is fabricated or uncorrectable, a
  customer cannot read their own issued boarding code, or a mounted server capability has no client
  caller. Formalised below as `isBugCondition`.
- **Property (P)** — the desired outcome for inputs satisfying C: a real name or an explicitly
  unresolved state, a persistently readable own-code, and a working typed client path.
- **Preservation** — every behaviour outside C: real supplied names, location updates, admin-created
  customers, driver/admin full-manifest OTP visibility, co-passenger code stripping, existing
  PATCH lifecycle guards, password login, and both static frontends.
- **Placeholder name** — a stored `Customer.name` matching `/^User \d{4}$/`, generated by
  `services/authService.js:146` from the last four phone digits. Not a name the customer chose.
- **Unresolved rider** — a rider for whom no real name exists. Represented as `null` end-to-end
  (`utils/tripView.js` `displayName()` already does this) and rendered as a distinct state, never as
  a string that reads like a name.
- **`riderIdentity`** — the new backend module `utils/riderIdentity.js` that owns the placeholder
  predicate and the name resolver, so neither is duplicated.
- **`riderDisplayName()`** — the existing client resolver in `client/lib/geo.ts` that returns
  `string | null`. The client-side counterpart of `displayName()`.
- **`BoardingCode`** — the boarding OTP the driver asks for at pickup. `RideRequest.otp.code` for
  on-demand Flexy rides; `Trip.passengers[].otp.code` (surfaced as `myEntry.otp`) for scheduled
  subscription trips.
- **Booking** — a synonym for a **subscription**, not a third entity. `POST /api/v1/book` and
  `GET /api/v1/booking` are the subscription endpoints: `bookingController.getMyBooking`
  (`controllers/bookingController.js:135-160`) queries
  `Subscription.find({ customerId, status: { $in: CURRENT_STATUSES } })` and returns Subscription
  documents — the primary one flattened at the top level, the full list under `data.subscriptions`.
  A `Subscription` carries **no** boarding code; the code lives on the daily `Trip` documents
  generated from it (`services/DailyTripGenerator.js:64` sets
  `otp: { code: generateRideOtp(), verified: false }` per `Trip.passengers[]` entry), and reaches the
  customer through `GET /api/v1/customer/trips` → `toTripView` → `myEntry.otp`. So there is no
  `Booking` model to add and no OTP field to add to `Subscription`: the gap is the missing merge of
  the two journey sources into one upcoming view, plus one booking-related surface that renders no
  code at all.
- **Upcoming view** — the customer's single chronological list of journeys they still have ahead,
  merging both sources: subscription/booking `Trip`s and on-demand `RideRequest`s (2.20, 2.21).
- **`toTripView`** — `utils/tripView.js`, the shared trip serializer. Both static frontends read its
  legacy aliases, so any change to it is a shared-contract change (requirement 3.15).

## Bug Details

### Bug Condition

The bug manifests in three disjoint families of interaction. A rider's identity is fabricated or
uncorrectable; a customer holds a ride whose boarding code has been issued but cannot read it in the
client app; or the client cannot reach a server capability that is mounted and working.

**Formal Specification:**

```
FUNCTION isBugCondition(input)
  INPUT:  input — an interaction: { actor, surface, action, payload, storedState }
  OUTPUT: boolean

  RETURN isIdentityBug(input)
      OR isBoardingCodeBug(input)
      OR isUnwiredCapabilityBug(input)
END FUNCTION


FUNCTION isIdentityBug(input)
  // 1.1 — a blank name at OTP sign-up is accepted and replaced by a generated label
  RETURN (input.action = 'OTP_SIGNUP' AND isBlank(input.payload.name)
          AND accountIsCreated(input))

  // 1.2 — a supplied name is discarded for an already-registered customer
      OR (input.action = 'OTP_SIGNIN' AND NOT isBlank(input.payload.name)
          AND accountExists(input) AND storedNameUnchanged(input))

  // 1.3 — no API accepts a name change
      OR (input.action = 'UPDATE_PROFILE' AND input.payload CONTAINS 'name'
          AND storedNameUnchanged(input))

  // 1.4/1.5/1.6 — a fabricated label reaches a surface, or a placeholder is denormalized onward
      OR (rendersRiderIdentity(input.surface)
          AND resolvedRiderName(input) = null
          AND displayedRiderLabel(input) != UNRESOLVED_STATE)

  // 1.7 — the customer's own unset name is presented as if it were their name
      OR (isCustomerOwnSurface(input.surface)
          AND resolvedOwnName(input) = null
          AND displayedOwnLabel(input) != PROMPT_TO_SET_NAME)
END FUNCTION


FUNCTION isBoardingCodeBug(input)
  // 1.8/1.9/1.10 — the code exists server-side but no client surface reads it durably
  RETURN (input.actor = 'customer'
          AND hasIssuedBoardingCode(input.storedState)
          AND NOT codeReadableAfterReload(input.surface))

  // 1.11 — copy promises an OTP the surface never renders
      OR (input.surface = 'customer/dashboard'
          AND surfacePromisesOtp(input.surface)
          AND NOT surfaceRendersOtp(input.surface))

  // 1.12 — a rendered code has no copy control
      OR (surfaceRendersOtp(input.surface) AND NOT surfaceOffersCopy(input.surface))

  // 2.11 — "not yet issued" is indistinguishable from "failed to load"
      OR (input.actor = 'customer' AND NOT hasIssuedBoardingCode(input.storedState)
          AND NOT surfaceDistinguishes('NOT_YET_ISSUED', 'LOAD_FAILED'))

  // 1.19/1.20/1.21 — a code is issued for a journey the customer holds, but that journey
  //                  never appears in the upcoming view, so the code is unreachable from it
      OR (input.actor = 'customer'
          AND EXISTS journey IN customerJourneys(input.storedState)
              WHERE hasIssuedBoardingCode(journey)
                AND NOT isTerminal(journey)
                AND journey NOT IN upcomingView(input.surface))
END FUNCTION


FUNCTION isUnwiredCapabilityBug(input)
  // 1.13/1.14/1.15/1.16 — a mounted endpoint or returned field has no client consumer
  RETURN (endpointIsMounted(input.action) AND clientCallerCount(input.action) = 0)
      OR (input.action = 'BOARD_PASSENGER' AND usesNativePrompt(input.surface))
      OR (surfaceDisplaysHardcodedValue(input.surface))

  // 1.17 — a failed request renders as an empty result
      OR (requestFailed(input) AND renderedState(input.surface) = EMPTY_STATE)

  // 1.18 — the upload write path, recorded URL and serving route disagree
      OR (input.action = 'UPLOAD_DOCUMENT'
          AND (NOT directoryExists(configuredUploadPath())
               OR recordedUrl(input) NOT RESOLVED BY anyMountedRoute()))
END FUNCTION
```

### Examples

Identity:

- A customer signs up through the client modal, leaves Full Name empty because it carries no
  `required` attribute, and enters `9876543210`. Expected: the form refuses to submit. Actual:
  `Customer.name` is persisted as `User 3210` (`services/authService.js:146`).
- That same customer signs in a week later and types "Priya Sharma" into the name field. Expected:
  the placeholder is replaced. Actual: the existing-user branch (`:148-153`) reads only the stored
  name and ignores the supplied one.
- She opens the profile screen and tries to fix it. Expected: the name persists. Actual:
  `controllers/customerController.js:227` destructures `{ homeLocation, pickupLocation,
  dropLocation }`, so `name` is silently dropped and the response echoes the placeholder back.
- A driver opens a four-passenger shuttle. Expected: four distinguishable riders, with any unknown
  one visibly marked unavailable. Actual: `services/shuttleMatchingService.js:46,90` sends
  `'Unknown'`, `services/shuttleLifecycleService.js:57` sends `'Passenger'`,
  `client/app/driver/(dashboard)/assigned-trips/page.tsx:117` renders `'Customer'`, and
  `client/app/driver/(dashboard)/ride-queue/page.tsx:817,888,955,1012,1033,1064` renders raw
  `customerName` without `riderDisplayName()` — four rows that read like the same person.
- The driver's own sidebar shows `★ 4.85` for every driver in the fleet
  (`client/app/driver/(dashboard)/layout.tsx:78`).

Boarding OTP:

- A customer's Flexy ride is accepted; the toast reads `… accepted your ride! OTP: 481920`. They
  dismiss it and reload. Expected: the code is still on screen. Actual: it is gone — `activeRide`
  is socket-only state in `useRideBooking.ts` and no hook reads `/rides/active`.
- The dashboard's own step-3 copy says "Driver accepts trip → you get notified with OTP"
  (`client/app/customer/(dashboard)/dashboard/page.tsx:168`) and the file even imports the `Key`
  icon, while rendering no code anywhere.
- `CustomerRideDetailsPage` (`client/components/customer/CustomerPortalScreens.tsx:60`) renders
  status, route and driver, and no code.
- A customer holds one subscription trip for tomorrow (`Trip.passengers[i].otp.code = '204118'`,
  status `SCHEDULED`) and one on-demand Flexy ride accepted five minutes ago
  (`RideRequest.otp.code = '481920'`, status `ACCEPTED`). Expected: both appear under Upcoming in
  time order, each labelled with its source, each showing its own code. Actual: only the
  subscription trip is listed — `my-trips/page.tsx` reads only `useCustomerTrips`, and its
  `upcoming` filter at :108 admits only `SCHEDULED` / `IN_PROGRESS`, so the `ACCEPTED` ride is
  absent and `481920` is reachable nowhere in the app.
- A customer completes a booking and lands back on the subscribe page. Expected: the generated
  upcoming trips carry their codes, or say when codes are issued, and link to where they can be
  read. Actual: `subscribe/page.tsx:517` renders bare date chips only.
- Edge case, correct today and must stay correct: a customer reading a shared subscription trip sees
  their own `myEntry.otp.code` and no co-passenger's — `scopeOtp` in `utils/tripView.js` already
  reduces every other entry to `{ verified }`.

Unfinished integration:

- A driver taps to say they are approaching. Expected: `PUT /api/v1/driver/trips/status` with
  `ARRIVING`. Actual: there is no control; the endpoint has zero callers under `client/`, so
  `DRIVER_EN_ROUTE` and `DRIVER_ARRIVED` are unreachable from the portal.
- Boarding a passenger opens `window.prompt`
  (`client/app/driver/(dashboard)/current-trip/page.tsx:228`) — unstyled, untrappable, no error
  affordance.
- The wallet shows `₹ 0.00` with Add Money disabled and titled "not available in this API yet"
  (`client/components/customer/CustomerPortalScreens.tsx:31`), while
  `routes/v1/index.js:80-81` mounts `GET /wallet` (real `walletBalance` and transactions) and
  `POST /wallet/add`.
- A dashboard request 500s. Expected: a distinguishable failure. Actual:
  `client/app/customer/(dashboard)/dashboard/page.tsx:28` swallows it with `.catch(() => {})` and
  renders the same "No Active Commute" as a customer with no subscription.
- A driver uploads a licence. Expected: a stored file at a URL that resolves. Actual: multer writes
  to the relative, nonexistent `src/uploads` (`config/config.js:132`,
  `middleware/uploadMiddleware.js:6`), the controller records `/uploads/documents/<file>` while its
  `UPLOAD_DIR` (`controllers/documentController.js:9`) is `<repo>/../uploads/documents`, and `app.js`
  mounts no `/uploads` route at all.

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**

- A customer who supplied a real name keeps it verbatim on every customer and driver surface
  (3.1). The new overwrite rule fires only when the stored name is absent or matches
  `/^User \d{4}$/`.
- Trip manifests continue to resolve each rider from their `Customer` record and continue to return
  `null` rather than a placeholder (3.2). `utils/tripView.js` `displayName()` keeps its exact return
  contract; only its internals move behind `utils/riderIdentity.js`.
- `PUT /customer/profile` continues to validate and persist `homeLocation`, `pickupLocation` and
  `dropLocation` exactly as today, including every `validateLocation` rejection message (3.3).
  `name` is added alongside, not in place of.
- Admin-created customers keep their explicit names untouched (3.4). No admin path gains a
  placeholder-overwrite rule.
- `scopeOtp` keeps stripping co-passenger codes for `viewer: 'customer'` and keeps revealing every
  code for `viewer: 'driver' | 'admin'` (3.5, 3.6).
- `getMyRides`, `getRideById` and `getActiveRide` keep filtering on `customerId: req.user.id`
  (3.7). The new `matchedDrivers` projection removes a field; it does not widen a filter.
- `verify-otp` keeps rejecting an incorrect code and keeps refusing to board on the driver's word
  alone (3.8). The new entry affordance changes only how the code is collected.
- The existing PATCH start/complete endpoints and all their guards are untouched, including the
  refusal to complete while a boarded passenger has not been dropped (3.9). `updateTripStatus`
  already reuses those guards and is not modified.
- The customer ride-request socket path keeps validating, estimating and creating exactly as today
  (3.10); subscription purchase, pause, cancel and relocate are untouched (3.11).
- Password login and the non-customer OTP redirect are untouched (3.12, 3.13).
- `npm run check:contract` and `npm run test:unit` keep passing; the 14 known integration failures
  and 1 known `checkStartup` failure remain the only failures (3.14).
- Both static frontends keep working (3.15). Two specific traps: `customer frontend/js/auth.js:150`
  hides the name field and sends `name: ''` for a returning user, so the new-signup name requirement
  must apply **only** to the account-creation branch; and both frontends read `toTripView`'s legacy
  aliases (`manifest`, `tripDate`, `legacyStatus`), so those keys must survive unchanged.

**Scope:**

All interactions that do NOT satisfy `isBugCondition` are completely unaffected. Specifically:

- Any request by a customer whose stored `Customer.name` fails `/^User \d{4}$/` — the overwrite
  branch never runs.
- Any `PUT /customer/profile` body without a `name` key — identical code path and response.
- Any driver or admin read of a trip — full manifest, every boarding code, unchanged serialization.
- Any co-passenger's boarding code on any customer-facing payload — still stripped.
- Any password-authenticated sign-in, any subscription lifecycle operation, any existing
  PATCH trip transition.
- Both static frontends under `customer frontend/` and `driver frontend/`.

The correct behaviour for inputs *inside* the bug condition is specified in Correctness Properties
below.

## Hypothesized Root Cause

Root causes here are verified rather than hypothesised — every site below was read directly. The
open question is not *what* is wrong but *where the single owner of each rule should live*, which is
what this design settles.

1. **No single owner for "is this a real name?"** The placeholder is generated in one place
   (`services/authService.js:146`) and then reasoned about nowhere, so eight surfaces each invented
   their own fallback: `'Unknown'` (`sockets/customerEvents.js:37`,
   `services/shuttleMatchingService.js:46,90`), `'Customer'`
   (`sockets/customerEvents.js:159`, `assigned-trips/page.tsx:117`), `'Passenger'`
   (`services/shuttleLifecycleService.js:57`), `'Rider'` (`customer/(dashboard)/layout.tsx:66`,
   `customer/(marketing)/page.tsx:44`). `utils/tripView.js` `displayName()` is the one site that got
   it right, and nothing forces the others to agree with it.

2. **Write paths that read the request only partially.** `authService.verifyOtp` reads `name` inside
   the new-user branch only; `customerController.updateProfile` destructures three fields.
   Both are omissions of a field, not logic errors — which is why neither throws and both look
   correct in isolation.

3. **A client data layer that stops at the socket.** `useRideBooking.ts` receives `otp` on
   `ride:accepted` and stores it in React state. There is no query for it, so the code has the
   lifetime of a component. `queryKeys.ride.*` already exists and is unused, which shows the layer
   was planned and never built.

4. **Server work landing ahead of client work.** `PUT /driver/trips/status`, `GET /wallet`,
   `POST /wallet/add`, and the six extra `DriverProfile` fields are all live and correct;
   `scripts/contractCheck.js` already lists the first three under section 1 and reports them
   mounted. Nothing asserts that a mounted route has a caller, so the gap is invisible.

5. **Three independent opinions about one upload directory.** `config/config.js:132` defaults to a
   relative `'src/uploads'`; `controllers/documentController.js:9` computes
   `path.join(__dirname, '../../uploads/documents')` — outside the repo; the recorded URL assumes a
   static mount that `app.js` does not create. No single constant, so all three drifted.

## Correctness Properties

Property 1: Bug Condition - Identity, Boarding Code and Wiring Are Correct Under C

_For any_ input where the bug condition holds (`isBugCondition` returns true), the fixed system
SHALL produce the behaviour specified for that family: a rider is identified by a real stored name
or by an explicitly unresolved state that never reads as a name; a customer holding an issued
boarding code can read that code in full on the dashboard, my-trips and ride-detail surfaces and
still read it after a reload; and every mounted capability named in the requirements is reachable
from a typed client hook with a written upload location and a URL that resolves.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4, 2.5, 2.6, 2.7, 2.8, 2.9, 2.10, 2.11, 2.12, 2.13, 2.14, 2.15, 2.16, 2.17, 2.18, 2.19**

Property 2: Preservation - Behaviour Outside the Bug Condition Is Byte-Identical

_For any_ input where the bug condition does NOT hold (`isBugCondition` returns false), the fixed
system SHALL produce the same result as the original system, preserving real supplied names,
location-only profile updates, admin-created names, driver and admin full-manifest boarding-code
visibility, co-passenger code stripping, customer-scoped ride filtering, OTP verification rejection,
the existing PATCH lifecycle guards, subscription operations, password login, and both static
frontends.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 3.8, 3.9, 3.10, 3.11, 3.12, 3.13, 3.14, 3.15**

Property 3: Placeholder Overwrite Is Exactly Scoped

_For any_ pair of (stored name, supplied name) at OTP sign-in, the fixed `authService.verifyOtp`
SHALL persist the supplied name when the stored name is empty or matches `/^User \d{4}$/`, and SHALL
leave the stored name unchanged in every other case — including when the supplied name is blank,
whitespace-only, or itself placeholder-shaped.

**Validates: Requirements 2.2, 3.1, 3.4**

Property 4: No Fabricated Rider Label Reaches Any Surface

_For any_ rider whose name cannot be resolved, every payload and every rendered surface SHALL carry
`null` (server) or render the unresolved state (client), and SHALL NOT contain any of the literals
`Unknown`, `Passenger`, `Customer` or `Rider` in a rider-identity position.

**Validates: Requirements 2.5, 2.6, 2.7, 3.2**

Property 5: Boarding-Code Disclosure Is Requester-Scoped

_For any_ customer and any ride or trip in the store, every customer-facing response SHALL include
the requesting customer's own boarding code and SHALL NOT include any other rider's boarding code,
while every driver- and admin-facing response SHALL include all of them. This is asserted by test,
not assumed.

**Validates: Requirements 2.13, 3.5, 3.6, 3.7**

Property 6: Load Failure, Empty and Not-Yet-Issued Are Three Distinct States

_For any_ customer surface that reads ride, trip, wallet or boarding-code data, the rendered output
SHALL distinguish loading, request failure, genuinely-empty and not-yet-issued from one another, and
SHALL NOT render a failure as an empty result.

**Validates: Requirements 2.11, 2.18**

Property 7: Recorded Document URLs Resolve and Authorize

_For any_ successfully uploaded document, the file SHALL exist at the single configured storage
location, the recorded URL SHALL be served by a mounted route, and that route SHALL serve the file
only to the owning driver or an Admin.

**Validates: Requirement 2.19**

Property 8: The Upcoming View Holds Every Non-Terminal Journey, With Its Code

_For any_ customer and any combination of subscription/booking trips and on-demand rides they hold,
the **Upcoming tab (the upcoming view)** SHALL contain exactly the non-terminal journeys from both
sources — the merged list backing the my-trips screen as a whole may additionally carry terminal
rows, which the Completed and Cancelled tabs legitimately show — in one
chronological order with active journeys before terminal ones, each labelled with its
`source: 'SUBSCRIPTION' | 'ON_DEMAND'`, and each carrying its own boarding code when one has been
issued or an explicit not-yet-issued state when one has not — including on-demand rides in
`PENDING`, `ACCEPTED` and `DRIVER_ARRIVING`, and including the trips shown immediately after a
booking completes, which SHALL additionally link to the surface where codes can be read.

**Validates: Requirements 2.20, 2.21, 2.22**

## Fix Implementation

### Changes Required

Assuming the root-cause analysis above (verified, not speculative), the work is grouped by concern.
Ordering matters: shared modules first, then server write paths, then the client data layer, then
the surfaces.

---

#### A. `utils/riderIdentity.js` — new shared module (single source of truth)

**File**: `utils/riderIdentity.js` (new)

The predicate and the resolver both live here so neither is duplicated. Nothing else in the
codebase is permitted to contain the placeholder regex or a name fallback literal.

```
PLACEHOLDER_NAME_PATTERN = /^User \d{4}$/

isPlaceholderName(name)      -> boolean   // trims; '' and null are NOT placeholders, they are absent
isRealName(name)             -> boolean   // non-empty after trim AND NOT placeholder-shaped
resolveRiderName(ref)        -> string|null   // the only name resolver; returns null, never a label
shouldAdoptSuppliedName(storedName, suppliedName) -> boolean
        // true iff isRealName(suppliedName) AND NOT isRealName(storedName)
```

`shouldAdoptSuppliedName` is deliberately a pure two-argument function so Property 3 can be
property-tested exhaustively without a database.

**File**: `utils/tripView.js`

`displayName()` becomes a thin delegation to `resolveRiderName`. Its signature, its `null` return
and every key it emits stay exactly as they are — both static frontends and `contractCheck.js`
section 3/5 depend on them (3.2, 3.15).

---

#### B. Name capture and correction (2.1, 2.2, 2.3, 2.4)

**File**: `client/app/customer/(marketing)/page.tsx`

1. Add `required` and `minLength={2}` to the Full Name input at :72, matching the phone input
   beside it. Trim before submit and block submission on a whitespace-only value.
2. Replace the `'Rider'` fallback at :44 with the shared unresolved treatment (section D).

**File**: `services/authService.js`

3. New-user branch (:145-147): require a real name. `if (!isRealName(name)) throw 400
   'A full name is required to create your account.'` with a machine-readable `code:
   'NAME_REQUIRED'`. The generated `User ${phone.slice(-4)}` fallback is **deleted** — this is the
   only site that mints placeholders.
4. Existing-user branch (:148-153): `if (shouldAdoptSuppliedName(customer.name, name)) { customer.name = name.trim(); await customer.save(); }`
   then resolve `profileName` from the (possibly updated) record.
5. **Static-frontend guard (3.15):** the requirement in (3) applies only to account creation.
   `customer frontend/js/auth.js:150` hides the name field and posts `name: ''` for a returning
   user; that request must keep succeeding untouched. A returning user with a stale
   `localStorage.mobileNumber` but no account will now get a 400 — the `NAME_REQUIRED` code lets the
   Next client re-open the name step, and the static frontend surfaces the message through its
   existing `alert`.

**File**: `controllers/customerController.js`

6. `updateProfile` (:227): destructure `name` alongside the three location fields. Validate with a
   `validateName` helper mirroring `validateLocation`'s style: must be a string, trimmed length
   2–80, and rejected with `ValidationError` if placeholder-shaped (a customer must not be able to
   re-enter the broken state). Apply with `if (name !== undefined) customer.name = name.trim();`.
   Every existing location validation and message is left byte-identical (3.3).

**File**: `validations/` — no new Joi schema. `updateProfile` validates inline today and the
in-controller style is preserved rather than introducing a second validation mechanism for one
field.

**File**: `services/shuttleMatchingService.js`, `services/shuttleLifecycleService.js`,
`sockets/customerEvents.js`

7. Replace all five fabricated defaults (`:46`, `:90`, `:57`, `:37`, `:159`) with
   `resolveRiderName(...)`, carrying `null` onward (2.5). Where a ride is created and
   `ride.customerName` is absent, resolve from the `Customer` record before denormalizing (2.4)
   rather than defaulting.

**Migration decision for existing `User <last4>` rows** — required by the requirements, stated
explicitly:

- **No mutating backfill.** A real name cannot be invented, and `Customer.name` is
  `required: true` in `models/Customer.js:11-15`, so blanking placeholders would either need a
  schema change or would fail validation on the next `save()` of an untouched document. The risk of
  a bulk write against production identity data is not justified by the benefit.
- **Corrected on next sign-in**, by the rule in (4): the first time a customer with a
  placeholder signs in and supplies a name, the placeholder is replaced. This is the primary
  mechanism.
- **Prompted for in-app** (2.7): the customer dashboard and marketing greeting call
  `isPlaceholderName` on their own stored name and, when true, render "Add your name" linking to the
  profile screen instead of greeting a placeholder. This is the mechanism for customers who do not
  re-run OTP sign-in.
- **A read-only report script**, `scripts/migrations/reportPlaceholderNames.js`, that counts and
  lists affected `Customer` documents so the operator can size the problem. It writes nothing. If a
  mutating backfill is ever wanted, it is a separate, explicitly approved change.
- Driver-facing surfaces are not blocked on any of this: a placeholder that has not yet been
  corrected is recognised by `isPlaceholderName` at serialization time and carried as `null`, so it

## Testing Strategy

### Validation Approach

Two phases. First, write tests that fail on the unfixed code, which both proves the bug and confirms
the root-cause analysis. Then verify the fix holds for every input in the bug condition and that
nothing outside it moved. Property-based testing carries the preservation half, because the
interesting failures are edge cases in the placeholder predicate and the disclosure scoping, not the
happy path.

`test/` uses `node --test` with `mongodb-memory-server`; `fast-check` is available and already used
in `test/tripGenerator.property.test.js`. New tests follow the existing
`<feature>.exploration.test.js` / `<feature>.preservation.test.js` naming already established by
`customerOtpAccountRoleCorrection.*` and `customerPasswordLoginMismatch.*`, and are registered in
`package.json` under `test:unit` (no-DB tests) or `test:integration` (DB tests).

**Prerequisites, in order:**

1. `npm install` at the repo root (already satisfied) — `MONGODB_URI`, `JWT_SECRET` and
   `REFRESH_SECRET` must be exported for any backend run; no `.env.dev` exists in this clone, so a
   local `.env` is created from `.env.example` as a setup step.
2. **`npm --prefix client install`** — a hard prerequisite. `client/node_modules` is absent, so
   `next build`, `tsc --noEmit` and `npm run lint` cannot run for `client/` today, and the Next 16
   docs under `client/node_modules/next/dist/docs/` cannot be read. No client code is written before
   this completes.
3. Read the Next 16 guides listed in section H.

**Baseline to hold (3.14), confirmed against a clean `git archive HEAD`:** `npm run check:contract`
passes, `npm run test:unit` passes, `npm run test:integration` has 14 pre-existing failures
(Subscription validation: `pickupTime` / `subscriptionType` / coordinates required), and
`npm run check:startup` has 1 pre-existing failure (Socket.IO browser client). Every run is compared
against that count, not against zero.

**Goal**: Surface counterexamples that demonstrate the bug BEFORE implementing the fix, and confirm
or refute the root-cause analysis. If a test passes on the unfixed code, the corresponding root
cause is refuted and must be re-hypothesised.

**Test Plan**: `test/clientPortalIdentityAndOtp.exploration.test.js` drives the real service and
controller layers against `mongodb-memory-server`, asserting the *correct* behaviour so that each
assertion fails on today's code and names the defect in its failure message. Client-side gaps that
cannot be asserted server-side are covered by static assertions in `contractCheck.js`, which needs
no browser.

### Fix Checking

**Goal**: Verify that for all inputs where the bug condition holds, the fixed system produces the
expected behaviour.

**Pseudocode:**

```
FOR ALL input WHERE isBugCondition(input) DO
  result := fixedSystem(input)
  ASSERT expectedBehavior(result)
END FOR
```

Concretely, per family:

- **Identity** — for all (storedName, suppliedName) pairs, `shouldAdoptSuppliedName` agrees with the

### Preservation Checking

**Goal**: Verify that for all inputs where the bug condition does NOT hold, the fixed system
produces the same result as the original system.

**Pseudocode:**

```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT originalSystem(input) = fixedSystem(input)
END FOR
```

**Testing Approach**: Property-based testing carries this, because:

- it generates many cases automatically across the input domain, which is what a
  "must not clobber a deliberately-set name" rule needs;
- it catches the edge cases manual tests miss — `'User 12345'`, `'user 1234'`, `'  User 1234  '`,
  `'Users 1234'`, unicode names, a supplied name that is itself placeholder-shaped;
- it gives a real guarantee that behaviour is unchanged for all non-buggy inputs, rather than for
  the four cases someone thought of.

`fast-check` is already a dependency and already used in `test/tripGenerator.property.test.js`, so
the generator style follows that file.

**Test Plan**: Observe the unfixed behaviour first for real names, location-only profile updates,
driver/admin manifest reads and co-passenger stripping, then write the property tests capturing
exactly that behaviour in
`test/clientPortalIdentityAndOtp.preservation.test.js`.
